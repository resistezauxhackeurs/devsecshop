Monter le lab & construire sa première pipeline CI

Formation CI/CD & DevSecOps pour développeurs · Jour 1 · Durée estimée : 1 h 15
Objectifs de ce TP
  • Déployer l'application cible DevSecShop en local avec Docker.
  • Prendre en main l'application et configurer Burp Suite pour l'intercepter.

À ce stade, aucune sécurité dans la pipeline. On pose le terrain. Les TP suivants ajouteront un étage de sécurité à chaque fois.

Contexte

Pendant deux jours, vous attaquez et vous durcissez une seule application : DevSecShop, une boutique en ligne écrite en Node.js/Express, volontairement truffée de failles. Le principe de chaque TP est double :

Partie A — Comprendre & exploiter. Vous jouez l'attaquant, à la main, avec Burp.
Partie B — Détecter & corriger en CI/CD. Vous écrivez le job GitHub Actions qui aurait attrapé la faille avant la mise en production, puis vous corrigez le code jusqu'à ce que le build repasse au vert.

Les failles sont rangées en trois niveaux de difficulté de détection :

NiveauNatureComment on les trouve
1Failles classiques, visiblesEn lançant l'appli : Burp / scanner DAST (ZAP)
2Failles subtilesEn lisant le code : analyse statique (SAST)
3Logique métierNi l'un ni l'autre : raisonnement humain / tests d'abus

Le TP1 ne contient pas d'exploitation : c'est le montage du lab. Gardez vos identifiants et votre dépôt forké, ils servent jusqu'au TP8.

Prérequis

  • Docker et Docker Compose (docker --version, docker compose version).
  • Node.js 20 si vous voulez lancer l'appli hors Docker (node --version → doit afficher v20.x).
  • Burp Suite Community ou Pro.
  • Un compte GitHub (gratuit) pour forker le dépôt et exécuter la CI.
  • git installé et configuré.
Avertissement. DevSecShop est volontairement vulnérable. Ne l'exposez jamais sur Internet ni sur un réseau partagé. On travaille en local, point.

Déroulé

Récupérer et lancer le lab

Décompressez l'archive du TP. Le dossier devsecshop/ contient l'application. Lancez-la avec Docker :

cd devsecshop
docker compose up --build

Au premier lancement, l'image se construit (installation des dépendances). Quand vous voyez DevSecShop démarré sur http://localhost:3000, l'appli est prête. Ouvrez http://localhost:3000.

Sans Docker ? Vous pouvez lancer directement avec Node 20 : 
cd devsecshop
npm install          # Node 20 impératif (dépendance native libxmljs2)
npm start            # http://localhost:3000
Si npm install échoue sur libxmljs2, c'est que vous n'êtes pas en Node 20 : basculez avec nvm use 20. Détails dans le README de déploiement.

Configurer Burp Suite

On va router le trafic du navigateur vers Burp pour pouvoir l'intercepter et le rejouer.

  1. Dans Burp : onglet Proxy > Proxy settings, vérifiez l'écouteur sur 127.0.0.1:8080.
  2. Configurez votre navigateur (ou le navigateur intégré de Burp) pour utiliser ce proxy.
  3. Installez le certificat CA de Burp : rendez-vous sur http://burp > CA Certificate, puis importez-le dans le navigateur (nécessaire pour l'HTTPS, pas pour notre lab en HTTP mais prenez l'habitude).
  4. Dans Target > Scope, ajoutez http://localhost:3000 pour filtrer le bruit.
  5. Naviguez sur l'appli : vérifiez que les requêtes apparaissent dans Proxy > HTTP history.
Question 2. Interceptez votre requête de connexion (POST /login). Repérez le cookie session renvoyé. À votre avis, que contient-il ? (On le décortiquera au TP sur les secrets.)
Correction 2

Un JWT, pas un identifiant opaque

Le cookie session est un JWT : trois segments encodés en base64url séparés par des points (en-tête.payload.signature). Collé dans le Decoder de Burp (ou sur jwt.io), le payload se lit en clair :

{ "uid": 1, "username": "...", "is_admin": false }

Autrement dit, « cookie » ne veut pas dire « opaque » ni « chiffré » : ici le contenu est seulement signé (HS256). Seule la signature empêche de modifier le payload, et elle ne vaut que ce que vaut le secret qui la produit.

C'est le point de départ du TP2 : ce secret de signature est faible et présent dans le dépôt, donc forgeable. Au TP1, il suffit de comprendre que le cookie transporte une identité lisible.

Forker le dépôt et lancer la première pipeline

Créez un dépôt GitHub à partir du code fourni :

cd devsecshop
git init
git add .
git commit -m "Import DevSecShop (base du lab)"
# Créez un dépôt vide PRIVÉ sur GitHub, puis :
git remote add origin git@github.com:VOTRE_COMPTE/devsecshop.git
git branch -M main
git push -u origin main
Créez le dépôt en privé : il contient un fichier .env et des secrets (c'est voulu, c'est la matière du TP2, mais ça ne doit pas finir sur un dépôt public).

Le dépôt contient déjà un workflow .github/workflows/ci.yml. Allez dans l'onglet Actions de votre dépôt GitHub : la pipeline CI s'est déclenchée au push. Ouvrez-la et observez les étapes : Install → Lint → Tests → Build.

Lisez le workflow. Ouvrez .github/workflows/ci.yml et repérez : le déclencheur (on: push / pull_request), le runner (ubuntu-latest), la version de Node épinglée, et l'enchaînement des steps. C'est le squelette que vous enrichirez à chaque TP.
Question 3. La pipeline est-elle verte ? Que vérifie-t-elle réellement aujourd'hui en matière de sécurité ? (Indice : rien. C'est le point de départ.)
Correction 3

Verte, mais aveugle à la sécurité

La pipeline est au vert. Son workflow actuel enchaîne install → lint → test → build, mais :

  • le lint est lancé en || true : il n'échoue jamais, quoi qu'il trouve ;
  • le seul test est un smoke test (l'appli démarre sans planter) ;
  • aucun contrôle de sécurité : ni secrets, ni SAST, ni dépendances, ni DAST.

Le message à retenir : une CI verte ne dit rien sur la sécurité tant qu'on n'y a pas ajouté de contrôle de sécurité. C'est tout le fil rouge des 7 TP suivants : rendre cette pipeline capable de bloquer du code vulnérable.

Ce que vous devez rendre

  • Les réponses aux questions 1 à 3.
  • Une capture de votre pipeline Actions au vert sur votre fork.
  • Une capture de l'HTTP history de Burp montrant une requête interceptée vers localhost:3000.

Pour aller plus loin (facultatif)

  • Modifiez le message d'un step du workflow, poussez, et vérifiez que la pipeline se relance seule.
  • Ouvrez src/routes/ et parcourez les commentaires : chaque faille est annotée ⚠️ VULN. Résistez à l'envie de les corriger — on le fera dans l'ordre, TP par TP.
