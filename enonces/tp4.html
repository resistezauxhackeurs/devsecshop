Partie A — Comprendre & exploiter

Ces fonctions sont dans le back-office. Connectez-vous en admin (SQLi du TP3 : admin'-- -) avant d'attaquer.

A.1 — SSRF via l'import d'image

Le back-office « importe une image depuis une URL » : le serveur va chercher l'URL que vous fournissez. Rien ne l'empêche de viser le réseau interne. Le lab démarre un service interne (internal-metadata) non exposé publiquement :

GET /admin/import-image?url=http://internal-metadata:5678/
# ou, hors docker, un service local :
GET /admin/import-image?url=http://127.0.0.1:5678/
# cible classique en cloud (métadonnées) :
GET /admin/import-image?url=http://169.254.169.254/latest/meta-data/

La réponse renvoie le contenu du service interne : vous avez fait parler le serveur à sa place.

Question 1. Quelle donnée interne avez-vous récupérée ? En quoi la SSRF est-elle dangereuse en environnement cloud ?
Correction 1

Donnée récupérée

En visant http://internal-metadata:5678/, le service interne du lab renvoie son secret, du type SECRET-INTERNAL-TOKEN=.... Ce service n'est joignable que depuis le réseau Docker : c'est bien le serveur qui est allé le lire, pas vous.

Pourquoi c'est critique en cloud

  • La SSRF transforme le serveur en relais vers tout ce qu'il peut joindre : back-ends, bases, services internes non exposés.
  • En cloud, l'URL http://169.254.169.254/latest/meta-data/ expose les credentials IAM temporaires de l'instance → prise de contrôle potentielle du compte cloud.
  • C'est aussi un point de pivot : depuis l'extérieur, l'attaquant atteint des cibles internes normalement inaccessibles.

A.2 — XXE via l'import de catalogue

L'import de catalogue parse du XML avec les entités externes activées. On déclare une entité qui lit un fichier :

POST /admin/import-catalog    (Content-Type: application/xml)

<?xml version="1.0"?>
<!DOCTYPE catalog [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<catalog><product><name>&xxe;</name></product></catalog>

Le nom de produit renvoyé contient le contenu de /etc/passwd. On peut aussi viser une URL interne (XXE → SSRF).

Question 2. Montrez la fuite de fichier. Quelle option du parseur rend l'attaque possible ?
Correction 2

La fuite

Le nom de produit renvoyé dans la réponse contient le contenu de /etc/passwd : l'entité externe &xxe; a été résolue et substituée dans le document.

L'option fautive

Le XML est parsé avec la substitution d'entités activée (noent: true) et le chargement de DTD externe (dtdload: true). C'est ce couple qui autorise <!ENTITY xxe SYSTEM "file:///etc/passwd"> à lire un fichier du serveur. Note : le nom noent est trompeur, car mis à true il active la résolution des entités.

La même technique peut viser une URL interne (file:// → http://), transformant la XXE en SSRF.

💡 Théorie & méthode — SSRF

On ne peut pas faire confiance à une URL fournie par l'utilisateur. Le principe : allowlist plutôt que blocklist de chaînes. On valide le schéma (http/https seulement, ce qui bloque file:, gopher:…), on résout l'hôte en IP et on refuse toute IP privée, loopback ou link-local (dont 169.254.169.254), et on ne suit pas les redirections (une 3xx vers une IP interne serait un contournement).

Fonctions / outils à utiliser : new URL() (schéma + hostname), dns.lookup(host, {all:true}) (résolution), un test d'IP interne maison, http.get sans suivi de redirection.

À toi (SSRF). Écris le correctif puis vérifie (édite → docker compose up --build -d → ./scripts/test.sh). Si tu bloques, déplie la correction.
Voir la correction (code) — SSRF
// ❌ AVANT — le serveur va chercher N'IMPORTE QUELLE URL
router.get('/import-image', requireAdmin, (req, res) => {
  http.get(req.query.url, (r) => { /* renvoie le contenu */ });
});

// ✅ APRÈS — schéma validé, hôte résolu, IP interne refusée, pas de redirection
const dns = require('dns').promises;
const net = require('net');

function isBlockedIp(ip) {           // privée / loopback / link-local / réservée
  if (net.isIPv4(ip)) {
    const [a, b] = ip.split('.').map(Number);
    if (a === 10 || a === 127 || a === 0) return true;
    if (a === 169 && b === 254) return true;          // métadonnées cloud
    if (a === 172 && b >= 16 && b <= 31) return true;
    if (a === 192 && b === 168) return true;
    return false;
  }
  return true;                       // IPv6/inconnu : on refuse par défaut
}

router.get('/import-image', requireAdmin, async (req, res) => {
  let parsed;
  try { parsed = new URL(req.query.url); }
  catch (e) { return res.status(400).send('URL invalide.'); }

  if (parsed.protocol !== 'http:' && parsed.protocol !== 'https:')
    return res.status(400).send('Schéma non autorisé.');

  const records = await dns.lookup(parsed.hostname, { all: true });
  if (records.some((r) => isBlockedIp(r.address)))
    return res.status(403).send('Destination interne interdite.');

  // ... http.get SANS suivre les 3xx (une 3xx -> 400 « Redirection refusée »)
});

💡 Théorie & méthode — XXE

Une XXE vient du parseur, pas du XML. La parade : parser sans résoudre les entités, sans charger de DTD externe et sans accès réseau. Les données d'entrée restent des données ; aucune entité SYSTEM ne peut lire un fichier ni appeler une URL.

Fonctions / outils à utiliser : les options du parseur libxmljs2 — noent:false (pas de substitution d'entités), dtdload:false (pas de DTD externe), nonet:true (pas de réseau).

À toi (XXE). Corrige les options du parseur puis vérifie (./scripts/test.sh : plus aucune fuite de /etc/passwd, l'import XML légitime marche toujours). Si tu bloques, déplie la correction.
Voir la correction (code) — XXE
const libxml = require('libxmljs2');

// ❌ AVANT — entités externes activées (XXE possible)
const doc = libxml.parseXml(xml, { noent: true, dtdload: true });

// ✅ APRÈS — pas de substitution d'entités, pas de DTD externe, pas de réseau
const doc = libxml.parseXml(xml, { noent: false, dtdload: false, nonet: true });

💡 Théorie & méthode — Dépendances

Une faille peut venir d'une dépendance, pas de ton code. On maintient les versions à jour en continu : npm audit en CI (échec sur high+) et Dependabot qui ouvre des PR de bump automatiques. Certaines versions ne sont bumpées qu'aux TP5/6, où l'on traite la faille applicative correspondante.

Fonctions / outils à utiliser : npm audit, npm audit fix, Dependabot.
