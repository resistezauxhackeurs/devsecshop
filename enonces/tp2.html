Partie A — Comprendre & exploiter

A.1 — Repérer les secrets

Un secret, c'est tout ce qui donne un accès : clé d'API, mot de passe, secret de signature. Cherchez-les dans le dépôt, code et fichiers de config :

# motifs classiques dans tout le dépôt
grep -rniE "api[_-]?key|secret|password|token|sk_lab_" --include='*.js' --include='*.env' .
cat .env

Vous devez trouver au moins : une clé type Stripe en dur dans src/lib/config.js, et le fichier .env commité (secret JWT, mot de passe de base).

Question 1. Listez les secrets trouvés, leur emplacement, et pour chacun : que permet-il concrètement ?
Correction 1

Secrets présents dans le dépôt

  • Clé type Stripe sk_lab_... : en dur dans src/lib/config.js. Permet d'appeler l'API de paiement au nom du marchand (créer des remboursements, lire des transactions).
  • JWT_SECRET (devsecshop-super-secret-2023) : dans .env commité, et en valeur par défaut dans le code. C'est la clé de signature des sessions : qui la connaît peut forger n'importe quel jeton, donc usurper n'importe quel compte (voir Q2).
  • DB_PASSWORD : dans .env. Donne un accès direct à la base si elle est jointe.

Le fichier .env étant versionné, ces secrets sont aussi dans l'historique git, pas seulement dans le working tree.

A.2 — Exploiter : forger un jeton d'administrateur

Le cookie session est un JWT signé en HS256 avec le secret JWT_SECRET… que vous venez de lire. Qui connaît le secret peut fabriquer n'importe quel jeton, donc se faire passer pour l'admin sans mot de passe.

Récupérez d'abord votre cookie de session actuel (connectez-vous en client), puis décodez-le dans Burp (Decoder) ou sur un décodeur JWT. Forgez ensuite un token admin :

# avec la CLI node (depuis le dossier devsecshop, jsonwebtoken est déjà installé)
node -e "console.log(require('jsonwebtoken').sign({uid:1,username:'admin',is_admin:true},'devsecshop-super-secret-2023'))"

Dans Burp, remplacez la valeur du cookie session par ce jeton et rejouez une requête vers /admin. Vous êtes administrateur.

Question 2. Preuve d'accès au back-office avec le jeton forgé (capture). Pourquoi un secret fort mais présent dans le code ne protège-t-il pas davantage ?
Correction 2

Forge du jeton admin

Le cookie session est un JWT HS256 signé avec JWT_SECRET. Connaissant le secret, on fabrique un jeton qui se déclare admin :

node -e "console.log(require('jsonwebtoken').sign({uid:1,username:'admin',is_admin:true},'devsecshop-super-secret-2023'))"

On colle ce jeton dans le cookie session et /admin répond 200 : accès au back-office sans mot de passe.

Pourquoi la force du secret n'y change rien

La robustesse d'un secret protège contre le devinement (brute force). Elle ne protège en rien contre l'exposition : un secret de 64 caractères aléatoires, s'il est dans le code ou le dépôt, est lisible par quiconque a accès au dépôt, mais aussi à un fork, à un artefact de build ou à une image Docker. Dès qu'il est exposé, un secret est compromis, quelle que soit sa longueur. La seule parade est de ne jamais l'écrire dans le code (voir Partie B).

Partie B — Détecter & corriger en CI/CD

🛠️ Comment appliquer une correction (pas à pas)

Tu modifies le code sur ta machine (le dépôt cloné), avec ton éditeur — jamais à l'intérieur du conteneur.

  1. Édite le fichier chez toi.
  2. Reconstruis + relance (le Dockerfile COPIE le code, donc --build) : 
    docker compose up --build -d
  3. Vérifie : rejoue l'attaque (doit échouer) ou lance ./scripts/test.sh (Windows : scripts\test.bat).
  4. Besoin d'aide : git diff main origin/solution/tp2.

B.1 — Scanner les secrets dans la pipeline

Ajoutez le workflow fourni .github/workflows/02-secrets.yml (gitleaks) et le fichier de config .gitleaks.toml à la racine. Poussez. Le job doit échouer : il trouve les secrets, y compris dans l'historique (fetch-depth: 0).

gitleaks scanne aussi les commits passés : supprimer un secret dans un nouveau commit ne suffit pas, il reste dans l'historique. D'où l'étape de purge plus bas.

B.2 — Bloquer avant le push (pre-commit)

B.3 — Corriger le code

💡 Théorie & méthode

Un secret ne vit jamais dans le code ni dans le dépôt. Le code lit ses secrets depuis l'environnement (variables injectées au déploiement par un gestionnaire de secrets) ; le dépôt ne versionne qu'un .env.example sans valeur, et .env est ignoré. En dev, à défaut de JWT_SECRET, on génère un secret aléatoire éphémère au démarrage : rien de secret n'est écrit sur disque.

Supprimer n'est pas révoquer. Un secret exposé est compromis pour toujours : l'historique git est immuable. Deux gestes obligatoires : (1) le révoquer/roter côté fournisseur (d'abord), (2) le purger de l'historique.

Fonctions / outils à utiliser : process.env.X, crypto.randomBytes(), git rm --cached, git filter-repo.

À toi. Sors les secrets de config.js, ignore .env, ajoute .env.example, puis purge l'historique. Vérifie : édite le code chez toi → docker compose up --build -d → ./scripts/test.sh, et relance le job gitleaks (doit repasser au vert). Si tu bloques, déplie la correction.
Voir la correction (code)

Sortir les secrets de config.js

// ❌ AVANT — secrets en dur dans le code
module.exports = {
  paymentApiKey: 'sk_lab_0123456789abcdefghijklmnop',
  jwtSecret: 'devsecshop-super-secret-2023',
  // ...
};

// ✅ APRÈS — lecture exclusive depuis l'environnement
const crypto = require('crypto');

module.exports = {
  // Clé de paiement : env uniquement, pas de valeur par défaut.
  paymentApiKey: process.env.STRIPE_SECRET_KEY || null,
  // Secret JWT : env en priorité ; sinon secret aléatoire éphémère (dev).
  jwtSecret: process.env.JWT_SECRET || crypto.randomBytes(32).toString('hex'),
  // ...
};

Puis ignorer .env (.gitignore fourni) et ajouter un .env.example sans valeur comme modèle.

Retirer .env du suivi + purger l'historique

# retirer .env du suivi (il reste en local) et committer
git rm --cached .env
git add .gitignore .env.example src/lib/config.js
git commit -m "security: secrets hors du code + .env ignoré"

# purge de l'historique (⚠️ réécrit l'historique)
pip install git-filter-repo
git filter-repo --path .env --invert-paths --force
# puis forcer le push et prévenir l'équipe (historique réécrit)

Effet de bord utile : une fois JWT_SECRET roté, le jeton forgé au A.2 ne fonctionne plus.

Corrigé complet de référence : git checkout solution/tp2. Théorie détaillée : Guide détection & correction §1 (Secrets).

B.4 — Vérifier

Relancez la pipeline après purge et correction : le job gitleaks doit repasser au vert. Le jeton forgé avec l'ancien secret ne doit plus fonctionner une fois JWT_SECRET roté.
