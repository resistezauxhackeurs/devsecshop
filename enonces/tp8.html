Partie A — Comprendre & exploiter

A.1 — IDOR sur les commandes

Connecté en client, accédez à une commande qui ne vous appartient pas en changeant l'identifiant d'URL :

GET /account/orders/1      # la commande #1 appartient à un autre client

Le serveur la renvoie : il vérifie que vous êtes connecté, mais pas que la commande est la vôtre. Aucun scanner ne « sait » que cette commande ne devrait pas vous être accessible.

A.2 — Mass assignment : devenir admin

La mise à jour de profil recopie tout le corps de la requête dans l'objet utilisateur. Ajoutez un champ que le formulaire n'expose pas :

POST /account/profile
email=moi@exemple.fr&is_admin=1

Vous venez de vous promouvoir administrateur. (Variante avancée : __proto__[is_admin]=1 — prototype pollution via le merge récursif.)

A.3 — Quantité négative

Ajoutez au panier une quantité négative : le total devient négatif (avoir indu).

POST /cart/add      product_id=1&qty=-5

A.4 — ReDoS

La validation du code promo utilise une regex à backtracking catastrophique (/^([A-Za-z0-9]+)+$/). Node étant mono-thread, une seule requête gèle tout le serveur :

POST /cart/checkout   coupon=AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA!
Déni de service total avec une requête légère. Aucun DAST ni SAST générique ne le détecte.
Questions 1 à 4. Preuve pour chacune des 4 failles. Pour chacune : pourquoi ni le DAST ni le SAST ne la détectent-ils ?
Correction 1 - IDOR sur les commandes

Preuve

Connecté en bob, GET /account/orders/1 renvoie la commande #1 qui appartient à alice. Le serveur vérifie l'authentification mais jamais la propriété de la ressource.

Pourquoi ni DAST ni SAST ne la voient

L'outil ne connaît pas votre modèle d'autorisation : pour lui, une requête authentifiée qui renvoie 200 est « normale ». La notion de « propriétaire légitime » est purement métier.

Correction 2 - Mass assignment

Preuve

POST /account/profile avec email=moi@exemple.fr&is_admin=1 promeut l'utilisateur : le code fusionne tout le corps (_.merge(user, req.body)). Variante : __proto__[is_admin]=1 (prototype pollution via le merge récursif).

Pourquoi ni DAST ni SAST ne la voient

La requête est syntaxiquement valide et le champ is_admin existe bien dans le modèle : rien n'est « anormal » à lire. Seule la connaissance de ce qui devrait être modifiable (métier) révèle l'abus.

Correction 3 - Quantité négative

Preuve

POST /cart/add avec product_id=1&qty=-5 : la quantité négative rend la ligne puis le total négatifs (avoir indu au checkout).

Pourquoi ni DAST ni SAST ne la voient

Un entier négatif est une entrée parfaitement valide techniquement. Seule la règle métier « une quantité est un entier positif borné » permet de qualifier -5 d'abus.

Correction 4 - ReDoS

Preuve

POST /cart/checkout avec un coupon type AAAA…A! (environ 38 A suivies d'un caractère non conforme) déclenche un backtracking catastrophique sur /^([A-Za-z0-9]+)+$/. Node étant mono-thread, l'event loop gèle : déni de service total avec une requête légère.

Pourquoi ni DAST ni SAST ne la voient

Le DAST n'envoie pas spontanément la chaîne pathologique précise ; le SAST générique ne sait pas qu'une regex donnée est à backtracking exponentiel sur cette entrée. Il faut connaître le motif dangereux (quantificateur imbriqué ([A-Za-z0-9]+)+).

B.1 — Les abuse-cases

Ces failles ne se détectent pas par un outil mais par des tests qui encodent le comportement malveillant. Ajoutez tests/abuse-cases.test.js (fourni) : IDOR refusé, is_admin non forçable, total ≥ 0, checkout < 1 s. Ces tests deviennent un rempart permanent contre les régressions.

B.2 — Corriger

  • IDOR : filtrer sur l'utilisateur (WHERE id = ? AND user_id = ?).
  • Mass assignment : liste blanche explicite des champs ; is_admin jamais pris du client (supprime aussi la prototype pollution). lodash.merge retiré.
  • Quantité : bornée à un entier 1..99, côté ajout et checkout.
  • ReDoS : regex linéaire et longueur bornée (/^[A-Za-z0-9-]{3,32}$/).

Remplacez src/routes/cart.js, src/routes/account.js et package.json par les versions fournies. Les quatre correctifs, dans le détail :

💡 Théorie & méthode - IDOR

Le principe

Être authentifié ne suffit pas : il faut toujours vérifier que la ressource demandée appartient à l'utilisateur courant. C'est un contrôle d'autorisation (qui a le droit), distinct de l'authentification (qui es-tu), et il se fait côté serveur.

Fonction à écrire : filtrer la requête par le propriétaire, et renvoyer 404 si rien ne correspond.

À toi. Corrige /account/orders/:id pour qu'un client ne voie que ses propres commandes.
Voir la correction (code)
// ❌ AVANT — on vérifie l'authentification, pas la propriété
const order = db.prepare('SELECT * FROM orders WHERE id = ?').get(req.params.id);
res.render('order-detail', { order });

// ✅ APRÈS — on filtre sur l'utilisateur courant (req.user.uid)
const order = db
  .prepare('SELECT * FROM orders WHERE id = ? AND user_id = ?')
  .get(req.params.id, req.user.uid);
if (!order) return res.status(404).send('Commande introuvable.');
res.render('order-detail', { order });

Source : src/routes/account.js. Théorie détaillée : Guide détection & correction §10 (IDOR).

💡 Théorie & méthode - Mass assignment

Le principe

Ne jamais fusionner req.body en entier dans un objet du domaine : l'attaquant ajoute les champs qu'il veut (is_admin, __proto__[is_admin]). On n'autorise qu'une liste blanche de champs, explicitement.

Fonction à écrire : sélectionner nommément les champs modifiables ; is_admin ne vient jamais du client.

À toi. Corrige POST /account/profile pour que seul email soit modifiable, et retire lodash.merge.
Voir la correction (code)
// ❌ AVANT — tout le body est recopié dans l'utilisateur
const _ = require('lodash');
_.merge(user, req.body);   // is_admin=1 ou __proto__[is_admin]=1 passent

// ✅ APRÈS — liste blanche : seul email est mis à jour
const email = typeof req.body.email === 'string' ? req.body.email : u.email;
db.prepare('UPDATE users SET email = ? WHERE id = ?').run(email, u.id);
// is_admin n'est jamais lu depuis le body ; lodash.merge est retiré du package.json.

Source : src/routes/account.js. Théorie détaillée : Guide détection & correction §11 (mass assignment).

💡 Théorie & méthode - Quantité / prix négatif

Le principe

Toute entrée numérique venant du client doit être validée et bornée côté serveur (type entier, minimum, maximum), à l'ajout comme au checkout, car le client peut rejouer la requête.

Fonction à écrire : parsing strict / Number.isInteger + bornes 1..99.

À toi. Borne la quantité à un entier 1..99, à l'ajout et au checkout.
Voir la correction (code)
// ❌ AVANT — la quantité vient du client sans contrôle
const qty = parseInt(req.body.qty, 10);   // -5 accepté → total négatif

// ✅ APRÈS — entier borné 1..99, réutilisé à l'ajout ET au checkout
function cleanQty(v) {
  const n = parseInt(v, 10);
  if (!Number.isFinite(n) || n < 1) return 1;
  return Math.min(n, 99);
}
const qty = cleanQty(req.body.qty);
// … et au checkout : total = Math.max(0, total);

Source : src/routes/cart.js. Théorie détaillée : Guide détection & correction §12 (prix négatif).

💡 Théorie & méthode - ReDoS

Le principe

Un quantificateur imbriqué comme ([A-Za-z0-9]+)+ provoque un backtracking catastrophique : sur une entrée qui ne matche pas, le moteur explore un nombre exponentiel de découpages et gèle le thread. On utilise une regex linéaire et une longueur bornée.

Fonction à écrire : rejeter d'abord sur la longueur, puis tester une classe simple sans quantificateur imbriqué.

À toi. Remplace la regex du coupon par une version linéaire et bornée.
Voir la correction (code)
// ❌ AVANT — quantificateur imbriqué → backtracking catastrophique
/^([A-Za-z0-9]+)+$/.test(code);

// ✅ APRÈS — longueur bornée puis regex linéaire
function validateCoupon(code) {
  if (typeof code !== 'string' || code.length > 32) return false;
  return /^[A-Za-z0-9-]{3,32}$/.test(code);
}

Source : src/routes/cart.js. Théorie détaillée : Guide détection & correction §13 (ReDoS).

B.3 — La gate de sécurité (le cœur du capstone)

Ajoutez .github/workflows/security.yml. Il rassemble tous les contrôles (secrets, SAST, SCA, tests d'abus) et un job final security-gate qui ne réussit que si tous passent. Puis activez la protection de branche :

Settings > Branches > Add branch protection rule
  Branch name pattern : main
  ☑ Require status checks to pass before merging
      → cocher "security-gate"
  ☑ Require a pull request before merging

Désormais, impossible de merger si une faille passe : la pipeline rouge bloque le merge.
