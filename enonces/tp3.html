Partie A — Comprendre & exploiter

A.1 — Bypass d'authentification

Le login construit sa requête en collant vos entrées dans la chaîne SQL. En commentant la fin de la requête, on se connecte sans mot de passe. Interceptez POST /login dans Burp et envoyez :

username = admin'-- -
password = (n'importe quoi)

Le -- commente le reste (la vérification du mot de passe). Vous êtes connecté en admin, accès /admin ouvert.

Question 1. Expliquez, requête SQL à l'appui, pourquoi admin'-- - fonctionne.
Correction 1

Ce que devient la requête

Le code assemble la requête par concaténation :

SELECT * FROM users WHERE username = 'admin'-- -' AND password = '...'

L'apostrophe de admin' ferme la chaîne du nom d'utilisateur. Le -- (avec l'espace) ouvre un commentaire SQL : tout ce qui suit, y compris AND password = '...', est ignoré. La requête devient en pratique :

SELECT * FROM users WHERE username = 'admin'

Elle renvoie la ligne admin → l'appli considère la connexion réussie, sans jamais vérifier le mot de passe.

Variante ' OR '1'='1

... WHERE username = '' OR '1'='1' AND password = '...' : la condition '1'='1' est toujours vraie → la requête renvoie (au moins) une ligne, souvent le premier utilisateur.

La cause racine

Les entrées utilisateur sont concaténées dans la requête : la donnée devient du code SQL. C'est la définition même de l'injection SQL (CWE-89).

A.2 — Exfiltration par UNION

La recherche produit est aussi injectable. On utilise un UNION SELECT pour faire renvoyer les colonnes de users à la place des produits. Le catalogue a 6 colonnes, on aligne le nombre :

GET /products/search?q=zzz' UNION SELECT id, username||':'||password, email, 0, '', 0 FROM users-- -

Les « produits » affichés sont en fait utilisateur:hash_md5. Les hash sont en MD5 (faible) : passez-les à un cracker (hashcat -m 0, ou une base de rainbow tables en ligne).

Question 2. Donnez les identifiants récupérés. Pourquoi le MD5 non salé est-il un problème en plus de la SQLi ?
Correction 2

Identifiants récupérés

  • alice → 5f4dcc3b5aa765d61d8327deb882cf99 = MD5(password)
  • bob → 0571749e2ac330a7455809c6b0e7af90 = MD5(sunshine)
  • admin → c2fe1ddfce87639e0d1eb1d1157070fe = MD5(S3cur3P@ss)

Un hashcat -m 0 sur une liste courante les retrouve en quelques secondes.

Pourquoi MD5 non salé aggrave tout

  • Rapide : MD5 se calcule par milliards/seconde sur GPU → brute force hors-ligne trivial.
  • Sans sel : deux utilisateurs avec le même mot de passe ont le même hash, et les rainbow tables (hash pré-calculés) donnent le mot de passe instantanément.
  • Effet cumulé : la SQLi donne l'accès aux hash ; MD5 non salé les transforme en mots de passe en clair, réutilisables ailleurs (credential stuffing).

Ce qu'il faudrait

Un hachage lent et salé conçu pour les mots de passe : bcrypt, argon2 ou scrypt (fonction bcrypt.hash() / argon2.hash()). Même exfiltrés, les hash restent coûteux à casser.

A.3 — Brute force du login

Aucune limite de tentatives : le login est brute-forçable. Dans Burp, envoyez un POST /login vers Intruder, placez le marqueur sur password, chargez une liste (ex. rockyou réduite). Le compte alice a un mot de passe du top-100.

# équivalent en ligne de commande (ffuf) :
ffuf -X POST -u http://localhost:3000/login \
  -d "username=alice&password=FUZZ" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -w rockyou-top1000.txt -mc 302 -fc 401
Question 3. Combien de tentatives avant de trouver le mot de passe d'alice ? Qu'est-ce qui rend l'attaque possible côté serveur ?
Correction 3

alice utilise password : il est dans les tout premiers d'une liste type rockyou → trouvé en quelques dizaines de tentatives (position ~1 à 10 selon la liste).

Ce qui rend l'attaque possible côté serveur

  • Aucune limite de tentatives (pas de rate-limit par IP/compte).
  • Aucun verrouillage de compte après N échecs, aucun délai progressif.
  • Pas de second facteur, pas de CAPTCHA, message d'erreur identique → rien ne ralentit l'attaquant.

Contre-mesures : limiter les tentatives (rate-limit), verrouillage/temporisation, MFA, et imposer des mots de passe forts.

B.1 — SAST : repérer la faille dans le code

La SQLi ne vient pas d'une dépendance mais de votre code. L'analyse statique la voit. Ajoutez la règle semgrep-rules/sql-injection.yml et le workflow .github/workflows/03-sast.yml. Testez en local :

# en local (si semgrep installé) :
semgrep scan --config ./semgrep-rules --config p/javascript src/

La règle maison repère db.prepare("..." + ...) et la forme en variable const sql = "..." + x; db.prepare(sql). Au push, le job Semgrep échoue et remonte les findings dans l'onglet Security (format SARIF).

Point clé : le DAST (Burp/ZAP) trouve la SQLi en attaquant l'appli ; le SAST la trouve en lisant le code, bien plus tôt dans le cycle. Les deux sont complémentaires.

B.2 — Corriger

Deux corrections à écrire dans src/routes/auth.js (et src/routes/products.js pour la recherche).

💡 Théorie & méthode

1) Requêtes paramétrées (contre la SQLi)

On sépare le code de la donnée : la requête contient des emplacements ?, et les valeurs sont envoyées à part. L'entrée est alors traitée comme une simple donnée et ne peut plus modifier la structure de la requête. C'est la seule parade fiable (échapper les quotes à la main ne suffit pas).

Fonction à utiliser (better-sqlite3) : db.prepare('… WHERE x = ?').get(valeur) — les ? sont liés aux arguments de .get() / .all() / .run().

2) Limiteur de tentatives (contre le brute force)

On plafonne le nombre de requêtes de login par IP sur une fenêtre de temps ; au-delà, l'app répond 429 Too Many Requests. L'attaque par liste devient trop lente pour aboutir.

Fonction à utiliser : le middleware express-rate-limit sur la route /login (ex. 5 tentatives / 15 min).

À toi. Écris les deux correctifs, puis vérifie : édite le code chez toi → docker compose up --build -d → ./scripts/test.sh. Si tu bloques, déplie la correction.
Voir la correction (code)

Requêtes paramétrées

// ❌ AVANT — concaténation (injectable)
const sql = "SELECT * FROM users WHERE username = '" + username +
            "' AND password = '" + hash + "'";
const user = db.prepare(sql).get();

// ✅ APRÈS — paramètres liés
const user = db
  .prepare('SELECT * FROM users WHERE username = ? AND password = ?')
  .get(username, hash);

Même idée pour la recherche produit (products.js) :

const products = db
  .prepare('SELECT * FROM products WHERE name LIKE ?')
  .all('%' + q + '%');   // q est une donnée, pas du SQL

Limiteur de tentatives

const rateLimit = require('express-rate-limit');

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,   // 15 minutes
  max: 5,                     // 5 tentatives par IP, puis 429
  standardHeaders: true,
  legacyHeaders: false,
});

router.post('/login', loginLimiter, (req, res) => { /* … */ });
npm install express-rate-limit    # déjà dans le package.json du corrigé
