Partie A — Comprendre & exploiter

A.1 — Bypass d'authentification

Le login construit sa requête en collant vos entrées dans la chaîne SQL. En commentant la fin de la requête, on se connecte sans mot de passe. Interceptez POST /login dans Burp et envoyez :

username = admin'-- -
password = (n'importe quoi)

Le -- commente le reste (la vérification du mot de passe). Vous êtes connecté en admin, accès /admin ouvert.

Question 1. Expliquez, requête SQL à l'appui, pourquoi admin'-- - fonctionne.

A.2 — Exfiltration par UNION

La recherche produit est aussi injectable. On utilise un UNION SELECT pour faire renvoyer les colonnes de users à la place des produits. Le catalogue a 6 colonnes, on aligne le nombre :

GET /products/search?q=zzz' UNION SELECT id, username||':'||password, email, 0, '', 0 FROM users-- -

Les « produits » affichés sont en fait utilisateur:hash_md5. Les hash sont en MD5 (faible) : passez-les à un cracker (hashcat -m 0, ou une base de rainbow tables en ligne).

Question 2. Donnez les identifiants récupérés. Pourquoi le MD5 non salé est-il un problème en plus de la SQLi ?

A.3 — Brute force du login

Aucune limite de tentatives : le login est brute-forçable. Dans Burp, envoyez un POST /login vers Intruder, placez le marqueur sur password, chargez une liste (ex. rockyou réduite). Le compte alice a un mot de passe du top-100.

# équivalent en ligne de commande (ffuf) :
ffuf -X POST -u http://localhost:3000/login \
  -d "username=alice&password=FUZZ" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -w rockyou-top1000.txt -mc 302 -fc 401
Question 3. Combien de tentatives avant de trouver le mot de passe d'alice ? Qu'est-ce qui rend l'attaque possible côté serveur ?

Partie B — Détecter & corriger en CI/CD

B.1 — SAST : repérer la faille dans le code

La SQLi ne vient pas d'une dépendance mais de votre code. L'analyse statique la voit. Ajoutez la règle semgrep-rules/sql-injection.yml et le workflow .github/workflows/03-sast.yml. Testez en local :

# en local (si semgrep installé) :
semgrep scan --config ./semgrep-rules --config p/javascript src/

La règle maison repère db.prepare("..." + ...) et les template strings. Au push, le job Semgrep échoue et remonte les findings dans l'onglet Security (format SARIF).

Point clé : le DAST (Burp/ZAP) trouve la SQLi en attaquant l'appli ; le SAST la trouve en lisant le code, bien plus tôt dans le cycle. Les deux sont complémentaires.

B.2 — Corriger

Remplacez src/routes/auth.js et src/routes/products.js par les versions fournies :

  • Requêtes paramétrées : db.prepare('... WHERE username = ? AND password = ?').get(user, hash). Les entrées ne peuvent plus modifier la structure de la requête.
  • Limiteur : express-rate-limit sur /login (5 essais / 15 min, puis 429).
npm install express-rate-limit   # nouvelle dépendance (déjà dans le package.json fourni)

B.3 — Vérifier

Les tests d'abus fournis (tests/sqli.test.js, tests/bruteforce.test.js) doivent passer :

npm test
  • admin'-- - renvoie désormais 401.
  • La recherche par UNION ne fuit plus aucun hash (mais la recherche normale marche toujours).
  • Après 5 tentatives, le login renvoie 429.
  • Semgrep repasse au vert sur le code corrigé.
Livrables : réponses Q1–Q3 ; captures Burp (bypass + UNION + Intruder) ; capture du job Semgrep rouge puis vert ; npm test au vert.
