Partie A — Comprendre & exploiter

A.1 — Le cookie de préférences

Connectez-vous (client), puis posez une préférence : POST /account/prefs (theme/lang). Un cookie prefs (base64) est créé. À la lecture (GET /account/prefs), le serveur le désérialise avec node-serialize — un format maison qui, contrairement à JSON, sait rematérialiser des fonctions. Et il les exécute.

A.2 — RCE via _$$ND_FUNC$$_

node-serialize exécute toute fonction marquée _$$ND_FUNC$$_ suivie de () (IIFE). On fabrique un cookie piégé :

# générer le payload (depuis le dossier devsecshop)
node -e '
const s=require("node-serialize");
const p={rce:"_$$ND_FUNC$$_function(){require(\"child_process\").execSync(\"id > /tmp/pwned.txt\")}()"};
console.log(Buffer.from(s.serialize(p)).toString("base64"));
'

Dans Burp, remplacez le cookie prefs par cette valeur et rejouez GET /account/prefs. Le serveur exécute votre commande (/tmp/pwned.txt est créé).

C'est une RCE complète. Un simple cookie = exécution de commandes sur le serveur. Et aucun scanner dynamique ne la détecte sans connaître le format maison.
Question 1. Preuve d'exécution (contenu de /tmp/pwned.txt). Pourquoi JSON.parse ne permettrait-il jamais ça ?
Correction 1

Preuve d'exécution

Après avoir rejoué GET /account/prefs avec le cookie piégé, le fichier /tmp/pwned.txt contient la sortie de la commande id (uid/gid du process serveur). La commande a donc bien été exécutée côté serveur : c'est une RCE complète déclenchée par un simple cookie.

Pourquoi JSON.parse ne permettrait jamais ça

JSON.parse ne sait produire que des données : objets, tableaux, chaînes, nombres, booléens et null. Aucune syntaxe JSON ne représente une fonction, donc rien n'est jamais exécuté à la lecture.

node-serialize, lui, utilise un format maison qui sait rematérialiser des fonctions : toute valeur marquée _$$ND_FUNC$$_ est reconstruite (via eval), et si elle est suivie de () (IIFE) elle est appelée immédiatement pendant la désérialisation. La donnée du cookie devient alors du code exécuté.

B.1 — SAST ciblé

Ajoutez semgrep-rules/insecure-deserialization.yml et .github/workflows/05-sast-deser.yml. La règle repère require('node-serialize') et tout .unserialize(...). Le build échoue tant que le code dangereux est là.

B.2 — SCA confirme

npm audit (TP4) signale déjà node-serialize comme paquet à problème. SAST + SCA pointent la même faille sous deux angles : code et dépendance.

B.3 — Corriger

Remplacez src/routes/account.js par la version fournie : les préférences passent en JSON (JSON.stringify / JSON.parse), qui ne construit que des données. Retirez la dépendance :

npm uninstall node-serialize   # (déjà retiré du package.json fourni)
Règle générale : ne jamais désérialiser de données venant du client avec un format capable d'instancier des objets/fonctions. JSON pour les données ; si vous devez transporter des objets riches, signez-les (HMAC) et validez le schéma.
💡 Théorie & méthode

La parade n'est pas de « filtrer » le cookie mais de changer de format. On ne désérialise jamais des données venant du client avec un format capable d'instancier des objets ou des fonctions. JSON ne transporte que de la donnée : il ne peut rien exécuter. Si vous devez transporter des objets riches, signez-les (HMAC) et validez le schéma à la lecture.

Fonction / outil à utiliser : JSON.stringify à l'écriture, JSON.parse à la lecture ; suppression de la dépendance node-serialize.

// ❌ AVANT — node-serialize désérialise (et exécute) le cookie

// ✅ APRÈS — JSON pur, aucune exécution possible

// lecture :
